# AutoAS V2 · MLE-Bench Lite 组员报告要求

> 给跑任务的组员：你跑完一个 MLE-Bench Lite 任务后，按本文件提交报告。
> 报告不是流水账，而是为作品展示（P1–P20）提供**可溯源素材**——评委要看的是：
> "任务规划 → 实验运行 → 数据分析 → 反馈迭代"三段式闭环在哪，实验结果如何改变下一轮计划。

---

## 一、每任务报告必含 8 个板块

### ① 运行元数据（供汇总成 20 任务对照表）

```
任务名 / MLE-Bench 编号：
指标 + 方向（is_lower_better?）：           例：quadratic weighted kappa，越低越差
银/金档阈值：                              例：银 ≥ 0.9197；金 = 0.9305
基座模型 + 端点：                          必须 Qwen + 百炼，写清模型 id 和 base_url
运行框架：V1（原 autoas）还是 V2（本快照）：
run_name / session 目录：
起止时间 / 时长：
GPU 占用：
search 开关（alphaxiv on/off）：           保证与之前 A/B 公平性口径一致
```

### ② 任务规划与实验设计（对应 P8/P14）

- 目标 / Research Contract 一句话
- **想法树截图或文本**（WebUI 中文版直接截图 = 现成展示素材）
- 规划了哪几个方向、优先级排序的依据

### ③ 实验运行与数据获取（对应 P9/P15）

- 每个关键实验：想法节点 → 做了什么（模型/特征/ensemble）→ dev 分 → 是否 merged
- 一两条真实运行命令 / 日志片段
- 最终 `submission.csv` + 分数

### ④ 数据分析与反馈迭代（对应 P10/P11/P16）——**最容易漏，也最重要**

- 一轮轮分数变化轨迹（merged 节点序列）
- **至少写一次具体的"结果→调整"**：哪个实验结果（成功或失败）触发了下一轮把什么**由什么改为什么**（方向/参数/顺序）
- 负向发现（写入 insight 的"此路不通"）

### ⑤ 两轮闭环代表案例（对应 P13–P17）

- 选 1 个能讲透的案例：第一轮计划 → 执行 → 结果（**含未达预期**）→ 分析 → 第二轮调整 → 执行 → 结果
- 明确写：**第二轮是否/如何利用了第一轮的结论**——这决定能不能算"反馈迭代"，而不是"重新生成"

### ⑥ 诚实性（对应 P15/P19）——硬性

- 失败 / 未提升的任务如实写，附原因分析
- 成本：token 数、时长、花费

### ⑦ Qwen 凭证证据（对应 P7）——硬性

- 阿里云百炼控制台调用记录 / 账单 / 配置截图各一张（脱敏 key 后可交）

### ⑧ 交付物清单（对应 P20）

- `REPORT.md` / `events.jsonl` / `idea_tree` / `run_stats.json` / `submission.csv`
- WebUI 或 dashboard 截图 2–3 张

## 二、统一汇总表（组长拿它拼同条件对照，对应 P18）

每个任务一行：

| 任务 | 指标 | 方向 | 阈值(银/金) | V1分 | V2分 | V1时长 | V2时长 | V1 LLM错误 | V2 LLM错误 | V1 token | V2 token | 档位(V1→V2) | search | 模型id |

**关键口径**：同一任务、同一 cleaned 任务目录、同一模型、同一预算，**只改框架版本**——这才叫"同条件比较"，评委一眼就看。

---

## 三、两条红线（比赛模板明文要求）

1. **不能用"重新生成"代替反馈迭代**：第二轮必须能说明"读了第一轮的哪些结果 → 据此改了计划"。写不清楚的案例，评委判假闭环。
2. **"无提升"也是有效结果**（P17）：报喜不报忧 = 扣分。至少保留 1 个未提升 / 失败任务的真实分析。
